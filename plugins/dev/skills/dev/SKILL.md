# dev — 개발 파이프라인 디스패처

`/dev <작업>` 호출 시 메인이 작업 성격을 분류해 세 파이프라인 중 하나로 안내한다. 디스패처 자체는 코드 변경을 하지 않으며 **분류 + AUQ + 위임 안내**만 수행한다.

## 세 파이프라인

| 파이프라인 | 구조 | 효용 축 | 호출 |
|---|---|---|---|
| **solo-pipeline** | 4단계 × 단계별 단일 sub-agent | 비용 최저 + 단계 분리 | `/solo-pipeline` |
| **team-pipeline** (flex) | 4단계 × 단계별 1~N명 자동 산정 | 검출·다관점 | `/team-pipeline` |
| **team-flat** (향후) | 단계 없음, N 워커 병렬 | wall-clock | `/team-flat` |

> 어느 것도 안 부르고 메인이 직접 처리하는 **"순수 solo"**(스킬 없음)도 여전히 유효함. 1~2줄 수정 같은 사소한 작업에는 디스패처를 거치지 말고 그대로 진행.

---

## 단계 0 — 작업 분류

### 분류 휴리스틱

순서대로 검사하고 처음 매칭되는 모드를 추천:

1. **team-flat** — 다음 신호 ≥1
   - "N개 파일에 같은 패턴 / 전부 / 일괄 / 한 번에"
   - codemod, rename, 마이그레이션 적용, 다국어 N개 locale, 보일러플레이트 N개
   - 사용자가 `flat` / `병렬로` / `동시에` 명시

2. **team-pipeline (flex)** — 다음 신호 ≥1
   - 신규 컴포넌트 / 아키텍처 결정 / 인터페이스 설계
   - 보안·성능 critical / PII / 인증 / 결제 / migration
   - 사용자가 `pipeline` / `다관점` / `검출` / `안전망` 명시
   - 영향 범위가 cross-layer (API+DB+UI 동시)

3. **solo-pipeline** — 위 둘에 해당 없음 + 다음 신호 ≥1
   - 1~3 파일 단순 수정·리팩터링·버그 수정
   - 단계 분리(설계→리뷰→테스트)의 가치는 있으나 다관점·병렬 불필요
   - 사용자가 `solo` 명시

4. **기본값**: 위 신호가 모두 약하면 **solo-pipeline** 추천 (가장 비용 효율적이면서 단계 디시플린 확보)

### AUQ — 분류 확정

- 질문: `"작업 분류: <추천 모드> 권장 (이유: <한 줄>). 어떻게 진행할까요?"`
- 옵션:
  - `<추천 모드> 진행 (Recommended)` — 해당 스킬 호출 안내
  - `다른 모드 선택` — 모드 직접 지정 (solo-pipeline / team-pipeline / team-flat)
  - `취소` — 디스패처 종료

### 위임 안내 (메인이 직접 호출 못 함)

디스패처는 스킬을 자동 호출하지 않는다. 확정 후 사용자에게 다음 stdout 안내:

```
[Recommended] 작업을 <모드>로 진행하려면 다음을 입력하세요:
  /<모드명> <작업 설명>

예시: /solo-pipeline 결제 API에 로깅 미들웨어 추가
```

사용자가 직접 해당 스킬을 호출하면 그 스킬이 자기 단계 0부터 시작.

## 디스패처 출력 형식

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  dev — 작업 분류
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  입력:       <작업 설명>
  매칭 신호:  <감지된 키워드·휴리스틱>
  추천 모드:  <모드>
  이유:       <한 줄>
  비용 추정:  <X.X×>
```

비용 추정 가이드:
- solo-pipeline: ~1.4~1.6×
- team-pipeline: ~1.6~3.2× (인원 산정 결과에 따라)
- team-flat: ~1.3× (단 토큰 합계 기준, wall-clock은 0.28×)

## 핵심 원칙

| 원칙 | 강제 수준 |
|------|-----------|
| 디스패처는 코드 변경·sub-agent 호출 금지 (분류 + 안내만) | [Critical] |
| AUQ로 사용자 확정 후에만 위임 안내 출력 | [Critical] |
| 추천 모드가 의심스러우면 `Recommended` 옵션을 보수적인 쪽으로 (solo-pipeline > flex > flat 순) | [Recommended] |
| 디스패처는 스킬을 자동 호출하지 않는다 — 사용자가 직접 `/<모드명>` 입력 | [Critical] |

## 인자

```
/dev <작업 설명>
```

옵션 없음. 단순 분류용. 모드별 세부 인자(`--architect N` 등)는 해당 스킬에서 받음.

## 예시

### 예시 1 — flex로 분류

```
사용자: /dev 결제 API에 PII 마스킹 미들웨어 추가

메인:   ━━━ dev — 작업 분류 ━━━
        입력:       결제 API에 PII 마스킹 미들웨어 추가
        매칭 신호:  PII + 결제 + 신규 미들웨어 → 보안·성능 critical
        추천 모드:  team-pipeline (flex)
        이유:       보안 신호 + cross-layer 가능성 → 다관점 검출 가치 큼
        비용 추정:  ~2.5~3.0×

        [AUQ] "team-pipeline 권장. 어떻게 진행할까요?"
사용자: 그대로 진행

메인:   [Recommended] 다음을 입력하세요:
          /team-pipeline 결제 API에 PII 마스킹 미들웨어 추가
```

### 예시 2 — solo-pipeline으로 분류

```
사용자: /dev 로그 메시지 한 줄 오타 수정

메인:   매칭 신호: 1줄 수정, 사이드 영향 없음
        추천 모드: solo-pipeline
        이유:      단계 분리는 유지하되 다관점·병렬 불필요
        비용 추정: ~1.4×

        [AUQ] → 진행
        → /solo-pipeline 로그 메시지 한 줄 오타 수정 안내
```

### 예시 3 — flat으로 분류

```
사용자: /dev 20개 컨트롤러에 동일한 로깅 데코레이터 부착

메인:   매칭 신호: "20개" + 동일 패턴 반복 → embarrassingly parallel
        추천 모드: team-flat
        이유:      병렬 워커로 wall-clock 5.5× 단축 가능
        비용 추정: ~1.3× (단, wall-clock 0.28×)

        [AUQ] → 진행
        → /team-flat 20개 컨트롤러에 동일한 로깅 데코레이터 부착 안내
```

## 메인 에이전트 행동 지침

- 분류 휴리스틱은 **결정론적**이 아닌 가이드. 사용자가 모드 키워드(`solo` / `pipeline` / `flat`)를 명시하면 그것을 최우선.
- 비용 추정은 대략값. 정확한 인원·비용은 해당 스킬의 단계 0에서 산정.
- 디스패처가 자기 판단으로 스킬을 호출하지 말 것. **반드시 사용자가 명시 입력**.
- 분류가 애매하면 보수적으로 (solo-pipeline > flex > flat).

---

## 연관 스킬

- `/solo-pipeline` — 4단계 × 단계별 단일 sub-agent (Architect=opus / Coder=sonnet / Reviewer=opus / Tester=sonnet)
- `/team-pipeline` — 4단계 가변 인원 팀 (단계별 1~N명 자동 산정)
- `/team-flat` — 병렬 워커 (향후 추가)

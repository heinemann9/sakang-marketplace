# /council — 4관점 의사결정

설계·기술 선택 결정이 모호할 때 사용한다. 4명의 sub-agent를 **대화 이력 없이** fresh 로 병렬 실행하여 각자의 관점에서 입장을 받아낸 뒤 메인이 종합한다.

## 사용 시점

| 적합 | 부적합 |
|---|---|
| monorepo vs polyrepo | 명확한 사실 조회 |
| 기술 스택 선택 (Postgres vs MySQL 등) | 단순 버그 수정 절차 |
| go / no-go 판단 | 코드 리뷰 (→ `team-pipeline`) |
| 마이그레이션 전략 결정 | 이미 결정된 사항 실행 |
| 트레이드오프가 큰 아키텍처 결정 | 1~3 파일 단순 수정 (→ `solo-pipeline`) |

## 절차

### Step 1 — 질문 프레이밍

사용자 입력(`$ARGUMENTS`)을 다음 3요소로 구조화한다. 누락 시 `AskUserQuestion` 으로 보충.

- **결정 사항**: 1~2문장으로 명확히 정의
- **제약 조건**: 시간 / 비용 / 팀 역량 / 기술 스택 등
- **관련 코드/문서**: 경로 또는 핵심 diff 발췌

### Step 2 — 4개 sub-agent 병렬 실행

**반드시 단일 메시지에서 `Agent` 도구를 4번 호출하여 병렬 실행한다.** 순차 실행 금지(anti-anchoring 의 핵심).

| 역할 | 관점 | 모델 |
|---|---|---|
| **Architect** | 장기 확장성, 시스템 설계, 기술 부채 | sonnet |
| **Skeptic** | 리스크, 실패 모드, 숨겨진 비용 | sonnet |
| **Pragmatist** | 구현 난이도, 일정, 팀 역량 | sonnet |
| **Critic** | 대안 제시, 기존 선택의 약점 공격 | sonnet |

각 sub-agent 프롬프트는 다음 템플릿을 사용한다(역할명만 바꿔서 4개 생성).

```
당신은 {역할}입니다. 다음 결정에 대해 {관점}에서 분석하세요.

[결정 사항]: {Step 1의 결정}
[제약 조건]: {Step 1의 제약}
[관련 코드/문서]: {Step 1의 경로/diff}

다음 형식으로 답변하세요 (300단어 이내):
- **Position**: 찬성 / 반대 / 조건부 + 1줄 요약
- **Reasoning**: 근거 3가지 (불릿)
- **Risk**: 이 입장의 최대 위험 1가지
- **Surprise**: 다른 사람이 간과할 수 있는 점 1가지

당신은 다른 관점의 답변을 보지 못합니다. 자신의 관점에만 충실하세요.
```

### Step 3 — 종합 판단

메인이 4개 결과를 수집하여 다음 형식으로 보고한다.

```markdown
## /council 결과 — {결정 사항 1줄}

### 입장 요약
| 역할 | Position | 핵심 근거 |
|---|---|---|
| Architect | 조건부 찬성 | ... |
| Skeptic | 반대 | ... |
| Pragmatist | 찬성 | ... |
| Critic | 조건부 반대 | ... |

### 합의점
- (4명 중 3명 이상 동의한 사항)

### 분기점
- (의견이 엇갈린 사항 — 의사결정자가 선택해야 할 축)

### 최종 추천
{메인의 종합 추천 + 근거}

### 결정 요청
사용자 판단 필요: {남은 선택지 N개}
```

## 규칙

- **anti-anchoring 보장**: 4개 sub-agent 는 반드시 동시 호출. 한 명의 답을 보고 다음 프롬프트를 조정하지 않는다
- **결과는 휘발성**: 본 스킬은 결과를 별도 파일로 저장하지 않는다. 보존이 필요하면 사용자가 ADR(Architecture Decision Record) 형식으로 직접 기록
- **3:1 또는 4:0** 은 강한 신호, **2:2** 는 사용자 판단 필요로 명시
- **300단어 제한**: sub-agent 응답 길이 제한을 유지(요약 강제 → 핵심 추출 용이)

## 다른 플러그인과의 관계

- **`solo-pipeline` / `team-pipeline`** — 결정 *후* 의 구현. 본 스킬은 결정 *전*
- **`prd`** — 제품 요구사항 수준 결정은 PRD 작성이 우선. 본 스킬은 *기술/설계* 의사결정에 사용
- **`dev`** — 디스패처가 의사결정 성격의 요청을 만나면 본 스킬을 추천할 수 있음
